# ADR 0001 — SQLite in dev, Postgres in prod, one portable DDL for both

Status: accepted · 2026-08-07 · Supersedes nothing · Relates to §19, §29

## Context

§19 specifies Postgres for Rings 1 and 3 and ClickHouse for Ring 2. Cycle 1 has to produce a
working registry with zero new dependencies and no infrastructure: `node:sqlite` ships in Node 25,
a Postgres cluster does not. The risk of developing against SQLite is the usual one — you discover
in month four that the schema only ever ran on the dev engine.

## Decision

**One set of migration files, written in the intersection of SQLite and Postgres syntax.** The
files in `ops/migrations/` are the production DDL; they are not a dev-only mirror to be re-derived
later. Rings 1, 2 and 3 all live in the same SQLite file in dev; in production Ring 2 moves to
ClickHouse and Rings 1/3 to Postgres, and the same statements are the starting point for both.

The portable subset:

| §19 (Postgres)              | Portable                          | Why |
|---|---|---|
| `CREATE TYPE … AS ENUM`     | `TEXT CHECK (x IN (…))`           | SQLite has no user types. Same rejection, better error message, and adding a value is a migration either way. |
| `bigserial PRIMARY KEY`     | `INTEGER PRIMARY KEY`             | See divergence D1. |
| `jsonb`                     | `TEXT` holding JSON               | Both engines will store it; only Postgres can index into it. Validity is the ingest layer's job. |
| `date`, `timestamptz`       | `TEXT` holding ISO-8601 UTC       | Lexical order == chronological order, so `<`, `MIN`, `MAX`, `BETWEEN` and range overlap all work on both. |
| `numeric(p,s)`              | `NUMERIC`                         | SQLite ignores precision and scale entirely; carrying them would be decoration. |
| `text[]`                    | `TEXT` holding a JSON array       | `legal_case.sections`, `ingest_run.anomalies`. |
| `DEFAULT now()`             | column is `NOT NULL`, no default  | Every clock is an argument (`migrate(db, nowIso)`), so a migration or an ingest run reproduces byte-for-byte in a test. |
| `EXCLUDE USING gist`        | a view + a test                   | See divergence D2. |
| `CREATE DOMAIN`             | the CHECK list, inlined twice     | `election_lifecycle` appears in `election` and `contest`. Duplication is the price of one dialect. |

## Divergences we accept, and what they cost

**D1 — `INTEGER PRIMARY KEY` auto-assigns on SQLite, not on Postgres.** `place_version.id`,
`party_version.id`, `alliance_version.id`, `person_merge.id`, `claim.id`, `ingest_run.id`,
`correction.id`. SQLite treats the column as a rowid alias and fills it on `INSERT … NULL`;
Postgres would raise not-null. Two consequences: ingest **always supplies these ids explicitly**
(which it wants anyway — deterministic ids make re-ingest idempotent), and the Postgres cutover
adds `ALTER TABLE … ALTER COLUMN id ADD GENERATED BY DEFAULT AS IDENTITY` per table. That ALTER is
mechanical, and it is the whole cost of this divergence.

**D2 — the `party_version` overlap constraint is not enforced by the engine.** §19 has
`EXCLUDE USING gist (party_id WITH =, daterange(valid_from, valid_to) WITH &&)`, which prevents two
versions of one party from claiming the same day. SQLite has neither exclusion constraints nor
range types, and a `CHECK` cannot see another row, so there is no portable constraint.

The invariant is **not** dropped. `001_registry.sql` defines:

```sql
CREATE VIEW party_version_overlap AS …   -- empty view == invariant holds
```

using half-open `[valid_from, valid_to)` semantics identical to Postgres `daterange`, with
`COALESCE(valid_to, '9999-12-31')` for open-ended versions. `migrate.test.ts` asserts the detector
actually fires on an overlapping pair (abutting ranges must *not* fire), and `registry:audit` runs
the view as one of its nine invariants and exits 1 when it returns rows. On the Postgres cutover the real `EXCLUDE` constraint is added and the
view stays as a cheap explanation of what it enforces. `alliance_version` has the same shape and no
constraint in §19 either; if it starts mattering, it gets the same view.

**D3 — `source` is created in `001_registry.sql`, not `003_provenance.sql`.** Migrations apply in
lexical order and Postgres resolves `REFERENCES` at `CREATE TABLE` time (SQLite defers to DML), so
the FK parent of half the registry has to exist in the first file. Ring 3's other five tables are
in 003. The ring boundary is conceptual, not one-file-per-ring.

**D4 — Ring 2 in dev is a row store.** `ReplacingMergeTree(revision)` becomes
`PRIMARY KEY (contest_id, candidacy_id, revision)`: a revised figure is a new row, the prior row
stays readable, "current" is `MAX(revision)` per pair, and nothing is ever `UPDATE`d in place —
which is the property §6.10's correction ledger actually depends on. `PARTITION BY` and
`LowCardinality` are dropped; they are physical-layout hints with no dev-scale effect.

**D5 — `citation.page_no` is `NOT NULL DEFAULT 0`.** §19 has it nullable *and* in the primary key,
which Postgres silently promotes to not-null while SQLite (a documented legacy quirk) would admit
NULLs and therefore duplicate citations. We take the stricter reading and give it a meaning: `0` is
"the whole document". Every PK column in these files is explicitly `NOT NULL` for the same reason.

## What is still not enforced by the schema, and where it went instead

Cross-table invariants a `CHECK` cannot express — §19 already routes these to the dbt test suite, and
here they are routed to `registry:audit`. They live as SQL in `INVARIANTS`
(`packages/mandate/src/ingest/resolve/index.ts`); every query counts VIOLATIONS, so 0 rows means the
invariant holds, `auditSample` returns each with its row count, pass/fail and the SQL that produced
it, and the CLI exits 1 when any of them returns rows. There are nine:

1. `convicted_requires_court_order` — `legal_case.stage='convicted'` ⟹ `source.kind='court_order'` (P5)
2. `vote_share_never_exceeds_100` — per contest revision. **One-sided on purpose**: the two-sided
   "sums to 100 ± 0.5" was unsatisfiable by construction because `src/data/historical-results.ts`
   supplies a truncated top-N (≤ 5 contestants). See ADR 0003 for the decision and its upgrade
   trigger (full candidate-level results landing).
3. `margin_is_rank1_minus_rank2` — split out of the share check so its 0 violations stay visible
4. `contest_epoch_matches_election_epoch` (P4: no cross-epoch contests)
5. `contested_place_version_has_crosswalk_to_current_epoch`
6. `booth_votes_not_more_than_result_votes`
7. `party_version_no_overlapping_validity` — D2's view, standing in for the dropped `EXCLUDE`
8. `party_version_no_two_open_ended_rows` — the case a reviewer proved reachable through D2
9. `queued_pair_names_two_live_persons` — `006_merge_queue_survives_merge.sql` dropped
   `person_merge_candidate`'s two person FKs (they cascaded a reviewer's work item away the moment a
   merge deleted the absorbed person) and nothing replaced them, so a `pending`/`deferred` row that
   names a person that no longer exists was caught by no constraint at all.

Measured 2026-08-08 on a fresh `registry:migrate` + `registry:ingest --fresh` + `registry:resolve`:
all nine return 0 rows, `invariantsFailed 0`, `registry:audit` exits 0. Two of the nine pass
vacuously and the ADR says so rather than claiming coverage it does not have: `booth_result` is empty,
and `delim-2008` *is* the current epoch so every contested `place_version` trivially has one.

What the schema *does* enforce, because these are the ones that cannot be allowed to fail even for
one query: `result.source_id`/`citation.source_id`/`affidavit.source_id`/`legal_case.source_id`
`NOT NULL` (P2), `candidacy UNIQUE (contest_id, person_id)` (the ER hard negative),
`contest UNIQUE (election_id, place_version_id)` (P4), and every declared foreign key — which is
why `open()` sets `PRAGMA foreign_keys = ON` before anything else touches the connection.

## Surrogate keys that must never be published

`party_version.id`, `claim.id`, `place_version.id` and `result`'s implicit rowid are
**database-local surrogates**. Both engines assign them in insert order, so a `--fresh` rebuild from
reordered input renumbers them. Measured on the real register on 2026-08-08, ingesting the same bytes
into two fresh in-memory databases with the input arrays reversed: **32 of 63** `party_version` ids
move when `parties` is reversed, and **18,831 of 22,414** `claim` ids move when `parties` and
`candidates` are. (The claim figure depends on which arrays were reordered; the party figure does
not. Neither is a promise — the promise is the paragraph below.)

They are stable *within one database* because every upsert matches on a natural key, not on the
surrogate — `party_version (party_id, valid_from)` and `claim.content_key`, both `UNIQUE` since
`005_provenance_honesty.sql`. That is what binds an id to one fact for the lifetime of that database
and stops a citation being inherited by a different claim. Both halves are tested: `B5` asserts no id
churn inside one database when the register shrinks and is reordered, `B5b` asserts that across two
fresh rebuilds in different input orders the natural keys and every candidacy's resolved party are
identical and that no claim subject is ever a `party_version`.

It is not enough to publish them. Anything that leaves the database — a permalink, an export, an API
response, a `citation.claim_id` in a footnote — must carry the natural key instead:
`claim.content_key`, or `party_id` + `valid_from`. Making these columns content-derived `TEXT` was
considered and rejected: `citation.claim_id` is an `INTEGER` foreign key in ring 3 and changing its
type is a table rebuild in both engines for a property no current surface needs. Revisit when the
first published permalink needs a claim id.

## Migrations are forward-only

§29. `schema_migration(filename, applied_at)`, lexical order, one transaction per file, no `down`.
A mistake is corrected by a new numbered file, never by editing an applied one — an applied file is
part of the audit trail of how production got its shape. Rolling back a shipped schema change on a
database with real rows in it is a restore, not a migration, and pretending otherwise with a
`down.sql` nobody has ever run is worse than admitting it.

## Alternatives rejected

- **Postgres in dev via Docker.** Correct, and it costs every contributor a daemon plus a compose
  file for a database that has 33 tables and no traffic. Revisit when the first Postgres-only
  feature lands (JSON path indexes, `EXCLUDE`, or partitioning) — that is the upgrade trigger.
- **An ORM/migration library (Prisma, Drizzle, Knex).** Would generate two dialects for us, and
  would also own the schema. The schema is the moat; it stays as SQL we can read, diff, and paste
  into `psql`.
- **A dev-only SQLite schema, hand-maintained beside the real Postgres one.** Two schemas drift.
  Nobody has ever kept two schemas in sync by intention.
