# ECI source reconnaissance — 2023–2026

Reconnaissance only. No importer was written, no registry table was touched, no row was imported. Every
statement below was measured against the live ECI site on **2026-08-11**, and every number is reproducible
with the probes in [ops/probe/eci/](../../ops/probe/eci/).

The question this answers is not "does ECI publish results" but **"can ECI's current and recent election
data be ingested deterministically, reproducibly and with provenance?"**

---

## 1. Source inventory

ECI runs four independent publishing systems. They differ in format, discovery and authority, and the
distinction matters more than any other fact in this document.

| # | Family | Host | What it holds | Type | Authority |
|---|---|---|---|---|---|
| **A** | Statistical reports | `www.eci.gov.in` | 460 spreadsheets across 37 election categories, 2023–2026 | **XLS (BIFF8) + XLSX**, each with a PDF twin | PRIMARY |
| **B** | Per-constituency reports & Index Cards | `www.eci.gov.in` | 1,610 documents — 543 GE-2024 Index Cards, 1,067 per-AC reports | **PDF only** | PRIMARY |
| **C** | Live results portal | `results.eci.gov.in` | The currently-active count, per constituency | **Static server-rendered HTML** | PRIMARY (provisional) |
| **D** | Schedule API | `www.eci.gov.in` | Announced dates + phases for every 2023–2026 assembly election | **JSON** | PRIMARY |
| **E** | Archive | `old.eci.gov.in` | Pre-2024 statistical reports, incl. four 2023 elections | HTML index, **downloads broken** | PRIMARY, unusable |

**Corpus size: 2,070 artefacts.** 460 carry a spreadsheet (and every one of those 460 also has a PDF);
1,610 are PDF-only.

## 2. Source URL patterns

**Discovery API** — base `https://www.eci.gov.in/eci-backend/public`, header `secret: ECI@MAIN825`
(a public constant in the site's own JS bundle, `main.f315321d.js`; `REACT_APP_API_HOST` and the key are
both literals there).

| Purpose | Request |
|---|---|
| Which states voted in which year | `GET /api/get-ac-election-state` |
| Announced schedule + phases | `GET /api/get-ac-election-details?iYear=<YYYY>&st_code=<S25>&election_id=3` |
| Every artefact of an election | `GET /api/election-result?category_id=<1..37>` |
| A CMS page (press notes) | `GET /api/get-election-data?page_seo_name=ae-2023-tripura` |
| A document by id | `GET https://www.eci.gov.in/eci/public/api/document?id=14752` |

**Artefact URLs are returned by the API and must not be constructed.** Two different shapes exist:

```
# GE 2024 — stable, human-readable path
https://www.eci.gov.in/eci-backend/public/all_files/GE-2024-statistical-report/33-Constituency-Wise-Detailed-Result.xls

# Everything else — carries an upload epoch that cannot be derived
https://www.eci.gov.in/eci-backend/public//all_files/election_report/
  General_Election_to_the_Legislative_Assembly_of_West_Bengal_2026_2026/10-Detailed_Results_1778165388.xlsx
                                                                                        ^^^^^^^^^^ upload epoch
```

The `public//all_files` double slash is what the API returns; record the URL exactly as received.

**Live portal** — deterministic, once the active portal slug is known:

```
https://results.eci.gov.in/                                  -> meta-refresh to the active portal
https://results.eci.gov.in/<PortalSlug>/index.htm            -> index of declared seats
https://results.eci.gov.in/<PortalSlug>/ConstituencywiseS04182.htm   -> table view  (BEST for parsing)
https://results.eci.gov.in/<PortalSlug>/candidateswise-S04182.htm    -> card view
https://results.eci.gov.in/<PortalSlug>/RoundwiseS04182.htm?ac=182   -> round-by-round EVM counts
```

`S04182` = ECI state code `S04` + constituency number `182`. State codes are fixed two-character
(`S01`–`S29`, `U01`–`U08`) and come from `get-ac-election-state`, so the per-constituency URL **is**
deterministically generable. The **portal slug is not** — `ResultAcByeAugust2026` today; it must be read
from the redirect.

## 3. Discovery mechanism

Fully deterministic, three requests deep, no search engine anywhere:

```
GET /api/get-ac-election-state                → { "2026": { "S25": "West Bengal", … }, "2025": …, "2024": …, "2023": … }
  └─ for each (year, st_code):
     GET /api/get-ac-election-details?iYear=&st_code=&election_id=3   → schedule, phases, dates
  └─ for category_id in 1..37:
     GET /api/election-result?category_id=      → every artefact URL, title, format, size
```

`get-ac-election-state` returned exactly 20 state-elections: 2023 × 5, 2024 × 8, 2025 × 2, 2026 × 5.

**Where discovery is incomplete.** `get-ac-election-state` lists only the Nov–Dec 2023 batch. The February
2023 elections (Tripura, Meghalaya, Nagaland) and Karnataka (May 2023) appear **only** as hardcoded CMS
slugs in the JS bundle (`ae-2023-tripura`, `ae-karnataka2023`, …), and those CMS pages carry a press note
and nothing else — no results. See §7.

## 4. HTTP / content behaviour

Measured, per family:

| | Statistical spreadsheets | Index Card / per-AC PDFs | Document endpoint | Portal HTML | JSON API |
|---|---|---|---|---|---|
| `Content-Type` | `application/vnd.ms-excel`, `…spreadsheetml.sheet` | `application/pdf` | `application/pdf` | `text/html` | `application/json` |
| `Content-Length` | yes | yes | yes | yes | yes |
| `Last-Modified` | **yes** (`Thu, 26 Dec 2024 05:27:52 GMT`) | yes | **no** | yes | no |
| `ETag` | no | no | no | no | no |
| `Accept-Ranges` | **yes** | yes | no | yes | — |
| `Cache-Control` | — | — | `no-cache, no-store` | `no-cache, no-store` | `no-store` |
| Byte-stable across refetch | **yes** | **yes** | **yes** | **yes** (see below) | n/a |

No `ETag` anywhere, so conditional fetching must use `Last-Modified` where present and fall back to
content hashing where it is not. `Accept-Ranges: bytes` on the spreadsheets means an interrupted 12 MB
download is resumable at the byte level.

**Is the data in the HTTP response?** Checked rather than assumed, per the brief:

- `results.eci.gov.in` — **yes.** Fully server-rendered. The constituency table arrives as a plain
  `<table>` with EVM / postal / total / % per candidate and a `<tfoot>` total. No JavaScript executes any
  part of it.
- `www.eci.gov.in` — **no.** A genuine React SPA: `<div id="root"></div>` and 2.9 MB of JS, zero content.
  But its backing JSON API is public and returns everything the SPA renders, so a headless browser is
  still unnecessary.

## 5. Hashability

Every source in the recommended path can be downloaded, byte-hashed, and re-hashed to the same value.
Verified by fetching twice and comparing:

| Artefact | SHA-256 | Refetch |
|---|---|---|
| GE 2024 report 33, Constituency Wise Detailed Result (`.xls`, 2,812,928 B) | `91010daf2f545c89b053a45ebf17f04c6a602e0017d0b81d20f4eb5c456a0fac` | **identical** |
| WB 2026 report 10, Detailed Results (`.xlsx`, 256,102 B) | `9493c8be1f5e9b24c5c5a7381db70e8501665a72970bf120267698e104e83dc3` | **identical** |
| Bihar-182-Bankipur by-election Index Card (`.xlsx`) | `08220ac6c52db4e1c6ca92f43f63760d48b80bcbe44fd1839a2dde3ec2afb319` | not retried |
| GE 2024 report 1, The Schedule (`.xls`) | `f3e24e8840d34ebd40eb40028f70596ca461387d6b4ca5dccb8890e6f917890d` | not retried |
| GE 2024 report 13, PC Wise Voters Turn Out (`.xls`) | `90718874c8882580c73010355c4f3d167d4ed1ec958f521a5be184ed7d214cf2` | not retried |
| Tripura 2023 press note (PDF via `document?id=14752`, 2,879,579 B) | `176898c9d301f0c2cb3e7644f8c27c9806d7f756aaec9a3d6f0ff5193c77067b` | **identical** |
| Live portal, `ConstituencywiseS04182.htm` | `70418e7a8f20006d20377ff016c30184dc6e5a9f7e316e1bce3ec69522a64104` | **identical** |

Every field the registry's `source` table wants is available: URL, retrieval timestamp, content type, byte
size, SHA-256, HTTP status. `Last-Modified` is available for the spreadsheets and absent for the document
endpoint. `ETag` is available nowhere.

**On the portal HTML.** Two fetches of a *declared* constituency were byte-identical, so a settled result
page is stable enough for provenance. It is **not** stable during counting: the page carries
`<meta http-equiv='refresh' content='300'>` and a "Status of EVM Round: 32/32" counter, so its bytes
change every few minutes until the count completes. A hash taken mid-count records a genuine observation
at a timestamp, not a stable document — which is the correct reading, but the pipeline must not treat it
as final. This is exactly the distinction the registry's `Result.revision` column exists for.

## 6. Available fields

Marked RAW (present verbatim), DERIVED (computable from RAW here), or ABSENT.

### Election

| Field | State | Source |
|---|---|---|
| election name | RAW | `cat_name`, `election_title` |
| year | RAW | category name, `iYear` |
| house | RAW | category name distinguishes Loksabha / Legislative Assembly |
| election type | RAW | category name distinguishes General / Bye |
| election occurrence | **DERIVED** | from the by-election window; ECI publishes no ordinal |
| state | RAW | `st_code` + name |
| polling dates | RAW | `date_of_poll` per phase; GE 2024 report 1 |
| counting date | RAW | `date_of_counting` |
| phase | RAW (number, date, seat count) · **ABSENT** (which constituency polled in which phase) | `phase`, report 1 |
| notification date | RAW for assembly · **ABSENT (machine-readable) for Lok Sabha** | `date_of_gazette_notification` |

### Constituency

| Field | State | Source |
|---|---|---|
| number | RAW | assembly report 10 has `AC NO.` directly; GE report 33 does **not** — join via report 13 (§7) |
| name | RAW | with the reservation marker appended, e.g. `MEKLIGANJ (SC)`, `Araku (ST)` |
| state | RAW | every row |
| district | RAW in Index Cards only · ABSENT in detailed-result reports | `Assembly Constituency of Bihar, District PATNA` |
| reservation / category | RAW | name suffix, and Index Card `182 (GEN) BANKIPUR` |

### Candidate

Name, gender, age, category, party, symbol — **all RAW**, on every detailed-result row.

For 2024 Lok Sabha, **8,359 of 8,359 candidates carry a declared age**. This is the authoritative claim
that the registry's 193,951 unsourced declared ages currently lack.

### Results

| Field | State |
|---|---|
| EVM votes | RAW (`GENERAL` column) |
| postal votes | RAW |
| total votes | RAW |
| vote percentage | RAW — three denominators for Lok Sabha (over electors / over votes polled / over valid votes), two for assembly |
| winner | **RAW** — report 2, *List of Successful Candidates* |
| margin | **RAW** — report 2, `WINNING MARGIN`, with the runner-up named |
| status | DERIVED per candidate; Index Cards give nominated / rejected / withdrawn / contested / deposit-forfeited counts by gender |

### Elector / turnout

Electors, votes polled, turnout, **male / female / third-gender turnout**, polling stations — all RAW.
GE 2024 report 13 carries all of them per PC; Index Cards carry them per constituency along with service
electors, NRI electors, Rule 49MA test votes, VVPAT-retrieved votes, proxy and tendered votes.

## 7. ECI 2024 Lok Sabha — the two source families compared

The brief asked which of the two families is better. They are not substitutes; **each is better at a
different thing, and a two-source strategy is the right answer.**

| | **Family A** — statistical reports (42 spreadsheets) | **Family B** — Index Cards (543 PDFs) |
|---|---|---|
| result ingestion | **best** — report 33, all 8,901 rows in one file | worse — 543 files, PDF |
| candidate ingestion | **best** — name, sex, age, category, party, symbol | equal content, 543× the work |
| provenance | **best** — one hash covers 542 constituencies | 543 hashes, no `Last-Modified` |
| completeness | 542 of 543 PCs (see below) | 543 of 543 |
| reproducibility | **best** — byte-stable, `Accept-Ranges`, machine-readable | text layer present but fragmented across 61 subset fonts |
| turnout | **best** — report 13, gender-split per PC | per-constituency, richer (service/NRI/proxy/tendered) |
| demographics | report 13 gender splits; report 17 assembly-segment electors | deepest per-constituency detail |

**Recommendation: ingest Family A. Use Family B only for fields Family A does not carry** — district, and
the EVM/VVPAT/postal-rejection breakdown. Neither is needed for v1.

Three concrete facts about Family A that any importer must handle:

1. **Report 33 has no PC number.** It identifies a seat as (State Name, PC Name). Report 13 carries
   `PC NO.` alongside the name. I verified the join: after stripping the reservation marker —
   `Araku (ST)` in report 13 vs `Araku` in report 33 — **542 of 542 constituencies resolve to a PC
   number, with zero (state, number) collisions.** The join is total, and it is the same
   strip-the-marker normalisation the registry already needed for `BISHNUPUR(SC)`.
2. **Surat is not in report 33.** BJP won it unopposed, so it has its own report (`2(A).Constituency Data
   Summary For PC-SURAT`), which records `Gujarat-S06`, `Surat-GEN`, `Const. No. 24`. 542 + 1 = 543. A
   validator that expects 543 rows in report 33 is wrong, not the data.
3. **Arunachal Pradesh 2024 ships 17 reports, not 14**, because 10 of its 60 seats were uncontested —
   hence extra "All 60 ACs" variants. Report count per election is not a constant.

report on either host — only 2003, 2008 and 2013 exist. Tripura, Meghalaya, Nagaland and Karnataka 2023

in the page description, but the attachment links are absent from the HTML and `?do=download` returns a
93 KB HTML page rather than a file. **Their existence is discoverable; their bytes are not retrievable.**

**Final vs provisional.** Every statistical report carries ECI's own disclaimer, quoted verbatim from the
Bankipur Index Card:

> These statistical reports are prepared only for academic and research purposes from the secondary data
> filled in the Index Cards. The primary data is in the statutory forms maintained by the concerned
> Returning Officers and the data kept in statutory forms is final.

So ECI itself classes these as **secondary to Form 20**. They are final in the sense that they do not
change after publication — but the registry must not describe them as the statutory record, and Form 20
remains a distinct, un-ingested source. The live portal (§C) is explicitly provisional and says so on
every page.

## 9. By-elections, re-polls and deferred polls

How ECI distinguishes them, and what identifier maps a result to the right election event:

| Case | How ECI marks it | Machine-readable? |
|---|---|---|
| **General election** | Category named `General Election to the Legislative Assembly of <State> <Year>` | yes |
| **By-election** | Category named `Bye Election…` + a **calendar window**; one xlsx per constituency titled `<State>-<ACNo>-<ACName>` | yes |
| **Countermanded / by-election reason** | Index Card row: *"Whether this is Bye election or Countermanded election?"* → `Yes`, and *"If yes, reason thereof"* → **`Resignation of Nitin Nabin`** | yes |
| **Re-poll** (booths re-polled inside an election) | GE 2024 report 16, *Details of Re-poll Held*: state, PC No, polling stations affected, **Date of Re-Poll**. Index Card: *"Date(s) Of Re-Poll, (if any)"* → `NA` | yes |
| **Deferred single constituency** | Two complete report sets: `Including AC 03` / `Excluding AC 03` (Rajasthan 2023), `Including AC 144` (WB 2026) | yes, by category name |

**The official identifier.** ECI does **not** publish a stable election-event id in any of these
responses. What it publishes instead, and what the importer must key on, is the triple:

```
(category_id, category name, artefact title)
```

`category_id` is stable and dense (1–37). The category name carries house, state, year, type and the
deferred-poll qualifier. The artefact title carries the report number, or for a by-election the
`<State>-<ACNo>-<ACName>` identity.

This maps cleanly onto the registry's existing event identity
`(jurisdiction, kind, house, year, occurrence)` — with one honest gap. `occurrence` is **derived**: for
by-elections it must come from the ordering of ECI's calendar windows ("Jan to June" before "July to
Dec"), because ECI numbers no rounds. That derivation is defensible and must be recorded as derived, not
presented as sourced.

A separate warning for the deferred-poll pairs: `Including AC 03` and `Excluding AC 03` are **not two
elections**. They are two publications of one election, differing by one constituency. Importing both as
events would recreate exactly the Bihar-2005 collapse in reverse — one election split into two. The
correct handling is to ingest the `Including` set and record the `Excluding` set as a superseded
publication of the same event.

## 10. Schedule and phase data

This is the strongest single finding, because it removes the last derived field from the home page.

`GET /api/get-ac-election-details?iYear=2026&st_code=S25&election_id=3` returns one JSON object **per
phase**:

```json
{
  "election_title": "General Election to the Legislative Assemblies of West Bengal",
  "date_of_gazette_notification": "2026-03-30",
  "last_date_of_nominations": "2026-04-06",
  "date_for_scrutiny_of_nominations": "2026-04-07",
  "last_date_for_withdrawal_of_candidatures": "2026-04-09",
  "date_of_poll": "2026-04-23",
  "date_of_counting": "2026-05-04",
  "date_before_which_election_shall_be_completed": "2026-05-06",
  "phase": 1,
  "no_of_ac": 152,
  "st_code": "S25"
}
```

| Field the brief asked for | State |
|---|---|
| notification date | **RAW** — `date_of_gazette_notification` |
| nomination deadline | **RAW** — `last_date_of_nominations` |
| scrutiny | **RAW** — `date_for_scrutiny_of_nominations` |
| withdrawal | **RAW** — `last_date_for_withdrawal_of_candidatures` |
| polling date | **RAW** — `date_of_poll` |
| counting date | **RAW** — `date_of_counting` |
| completion date | **RAW** — `date_before_which_election_shall_be_completed` |
| phase | **RAW** — `phase`, with `no_of_ac` seats in that phase |

**All 20 state-elections returned every one of those eight fields populated.** Nothing is derived from a
five-year term. `election_id=3` is the only working value — 1, 2, 4, 5, 6 return no data — so this
endpoint covers **assembly elections only**.

**Two gaps, stated precisely.**

- **Which constituency polled in which phase is ABSENT.** The `detailed_ac` field looks like an AC list
  but is a display abbreviation: WB phase 1 returns the literal string `"1,2,3,152"` — four items, not
  152. `no_of_ac` gives the phase's seat *count* only. So `Contest.phaseN` cannot be populated from this
  source, and per-phase seat counts are the most granular truth available.
- **Lok Sabha has no equivalent endpoint.** GE 2024 report 1 gives phase number, states per phase, PCs per
  phase, poll date and counting date — all RAW — but **not** notification, nomination, scrutiny or
  withdrawal. Those appear only in the press-note PDFs. For the Lok Sabha, the four pre-poll dates should
  be left **absent** rather than derived.

## 11. Reproducibility

| | Statistical spreadsheets | Index Card / per-AC PDFs | Schedule JSON | Live portal HTML |
|---|---|---|---|---|
| 1. discover it again | **yes** — `category_id` is stable | **yes** — same | **yes** | partly: slug from redirect |
| 2. download it again | **yes** | **yes** | **yes** | yes, while the portal is live |
| 3. hash it again | **yes** — verified identical | **yes** — verified identical | no — no document | **yes** once declared |
| 4. parse it again | **yes** — parsers below | text layer yes, layout hard | **yes** | **yes** — plain `<table>` |
| 5. prove which source produced each row | **yes** | **yes** | **yes**, as a JSON snapshot | **yes** |

Two honest "no"s:

- **The schedule API returns no document.** There is nothing to byte-hash but the response body itself.
  The pipeline must persist the raw JSON response as the artefact and hash that, with
  `retrieval_kind='fetched'` and `hash_kind='document_bytes'` over the stored bytes — the same treatment
  the registry already gives a fetched file. Absent a `Last-Modified`, re-running after ECI edits a date
  produces a different hash and a correction, which is the desired behaviour.
- **Archive artefacts fail step 2.** The four 2023 elections at `old.eci.gov.in` are discoverable and
  undownloadable. No amount of pipeline design fixes that.

## 12. Source quality

| Class | Source | Use |
|---|---|---|
| **PRIMARY** | `www.eci.gov.in` statistical reports, Index Cards, schedule API | **the whole Phase 1 import** |
| **PRIMARY (provisional)** | `results.eci.gov.in` | counting-day only; never overwrite a statistical-report row with it |
| **PRIMARY (unusable)** | `old.eci.gov.in` archive | nothing; downloads dead |

| TERTIARY | TCPD / Lokdhaba | already imported through 2022; **do not extend it into 2023–2026 to paper over the five missing elections** |

The five missing 2023 elections should stay **absent**. TCPD would be easier to scrape and is already

fact is worse than a missing one.

## 13. Rate limits

No throttling observed: **15 sequential requests with no delay, all HTTP 200**, 0.85–1.58 s each.
`robots.txt` at `www.eci.gov.in` is `User-agent: * / Disallow:` — an empty `Disallow`, so nothing is
excluded. `results.eci.gov.in` serves no `robots.txt` (404).

Recommendation regardless: **one connection, 250 ms between requests, `--retry 3` with backoff.** A full
cold pull is 2,070 artefacts and roughly 1.5 GB; at that spacing it is about 15 minutes of wall clock for
the 460 spreadsheets, which is the only set v1 needs. This is a public utility, and there is nothing to
gain from parallelism.

## 14. Failure and retry

| Failure | Handling |
|---|---|
| HTTP 5xx / timeout | retry 3× with backoff; then record `FETCH_FAILED` in the manifest and continue |
| `secret` header rejected | **hard stop.** The key is a bundle constant and can rotate; re-read it from `main.*.js` rather than retrying |
| Portal slug changed | re-read the meta-refresh from `results.eci.gov.in/` |
| Artefact URL 404 | the upload epoch changed → re-run discovery for that `category_id` |
| Hash differs from the recorded one | **not an error to work around.** Record `HASH_DRIFT`, keep both hashes, and treat the change as a correction requiring review — the rule `ops/geo/refetch-lokdhaba.sh` already follows |
| Parse yields 0 rows | fail the artefact, never import an empty success |
| `no_of_ac` disagrees with the seats found | record and report; do not "fix" either side (§18) |

## 15. Headless browser

**Not required.** The two places JavaScript appeared were checked rather than assumed:

- `results.eci.gov.in` renders results server-side; the `<table>` is in the response.
- `www.eci.gov.in` is a true SPA, but its backing JSON API is public and returns everything the SPA shows.

## 16. Is HTML parsing sufficient?

For the live portal, **yes** — one `<table>` with a fixed 7-column header and a `<tfoot>`. A regex over
`<tr>`/`<td>` is enough; no DOM library is needed. HTML parsing is **not** needed anywhere else in the
recommended path.

## 17. Must PDFs be parsed?

**No, for everything v1 needs.** All 460 spreadsheets have PDF twins that carry the same data. PDFs are
required only for the 1,610 PDF-only artefacts (Index Cards and per-AC reports), and every field they
carry that v1 uses is also in a spreadsheet.

## 18. Is OCR required?

**No.** I probed the Tripura press note: 86 streams, 84 inflated, **60,975 text-showing operators, 61 font
objects, 1 image**. It is a text PDF, not a scan.

But a text layer is not a text extractor. The runs come back fragmented — `'ECTION '`, `'OMMISSION O'`,
`'IND'` — because the drop-cap glyphs sit in different subset fonts. Reconstructing readable text means
handling `TJ` arrays, per-font `ToUnicode` maps and word-position inference: a real PDF parser, not a
regex. Since no v1 field needs it, **defer PDF text extraction entirely.**

## 19. Recommended parser libraries

**None. Zero new dependencies, consistent with the rest of this repo.** I proved this rather than
asserting it — three working probes, Node built-ins only:

| Probe | Reads | Result |
|---|---|---|
| [ops/probe/eci/read-xls.mjs](../../ops/probe/eci/read-xls.mjs) | BIFF8 `.xls` — OLE2/CFB directory + FAT/miniFAT chains, `BOUNDSHEET`, `SST` streaming across `CONTINUE`, `LABELSST`, `NUMBER`, `RK`, `MULRK`, `LABEL` | parsed GE 2024 report 33: **149,909 records, 9,675 shared strings, 8,901 data rows** |
| [ops/probe/eci/read-xlsx.mjs](../../ops/probe/eci/read-xlsx.mjs) | `.xlsx` — ZIP central directory + `inflateRawSync` + SpreadsheetML | parsed WB 2026 report 10: **3,455 shared strings, 3,516 rows** |
| [ops/probe/eci/pdf-text-layer.mjs](../../ops/probe/eci/pdf-text-layer.mjs) | PDF — inflates streams, counts text operators | answered §18 |

BIFF8 needs no decompression at all; `.xlsx` needs only `node:zlib`, which is built in. When promoted,
these belong at `packages/mandate/src/ingest/sources/spreadsheet/{xls.ts,xlsx.ts}` behind one
`readSheet(bytes): string[][]` seam, so the two formats are one caller's problem.

## 20. Proposed raw-source storage

Mirrors `.data/cache/lokdhaba/` and its manifest, which already works:

```
.data/cache/eci/
  discovery/
    get-ac-election-state.json
    schedule-<year>-<st_code>.json          # the raw API response, hashed as the artefact
    election-result-<category_id>.json
  artefacts/
    <category_id>-<category-slug>/
      <report-title-slug>.<xls|xlsx|pdf>
  manifest.tsv        # source_id, category_id, title, url, status, sha256, bytes, content_type,
                      # last_modified, http_status, retrieved_at
```

`manifest.tsv` is the resume log and the provenance ledger in one file, with `status` ∈
`OK | HASH_DRIFT | FETCH_FAILED | SKIPPED_UNCHANGED`.

## 21. Proposed normalized import structure

No schema change is needed. The mapping onto existing tables:

| ECI | Registry |
|---|---|
| category → one election event | `election` — `(jurisdiction, kind, house, year, occurrence)`; `occurrence` derived for by-poll windows |
| schedule JSON, per phase | `election.announcedOn / notifiedOn / countingOn`, `election_phase(n, pollDate, seatCount)` |
| `AC NO.` / `PC NO.` + name + reservation | `place_version` — `(jurisdiction, kind, epoch, number)`, epoch `delim-2008` |
| one seat × one election | `contest`; `phaseN` stays **NULL** — §10 |
| candidate name, sex, age, category | `person`, `candidacy.ageDeclared`, `candidacy.serialNo` (the `"1 Dadhiram Ray"` prefix) |
| party + symbol | `party_version`, `symbol`; unresolved labels to `candidacy.partyRaw` |
| GENERAL / POSTAL / TOTAL / % | `result.evmVotes / postalVotes / votes / voteShare` |
| report 2 winner + margin | `result.isWinner`, `result.margin` — RAW, not computed |
| electors, voters, gender splits, polling stations | `turnout` |
| Index Card by-election reason | `claim` on the election, cited to the Index Card |

Two parsing details that must not be skipped: the candidate name in assembly reports is prefixed with its
serial number (`"1 Dadhiram Ray"`, `"4 Nota"`) and must be split, not stored whole; and the constituency
name carries its reservation (`MEKLIGANJ (SC)`) — keep the source spelling in `canonical_name` and strip
only for matching, which is the rule the registry already follows.

## 22. Provenance strategy

One `source` row per artefact, which is what makes every imported row traceable:

```
kind            = 'eci_statistical_report' | 'eci_index_card' | 'eci_schedule' | 'eci_result_portal'
publisher       = 'Election Commission of India'
title           = "<category name> — <report title>"
url             = exactly as returned by the API, double slash and upload epoch included
retrieved_at    = fetch timestamp
doc_hash        = SHA-256 over the bytes as received
hash_kind       = 'document_bytes'          -- for all four kinds; we hold the bytes
retrieval_kind  = 'fetched'                 -- we fetched them ourselves
```

Every row imported cites the artefact it came from. Because the spreadsheets are byte-stable, a later
refetch can prove that a corrected value came from the same document as the value it corrected — the
property that made the electoral-geography repair defensible.

ECI's own "secondary to Form 20" disclaimer must ride along as a caveat on anything built from these
reports.

## 23. Idempotency strategy

The artefact's identity is `(category_id, report title)` — **not** the URL, which carries a mutable upload
epoch. Re-running:

1. Discovery re-reads the 37 categories.
2. For each artefact, compare `Last-Modified` (where sent) and then the stored `doc_hash`.
3. Unchanged → `SKIPPED_UNCHANGED`, no re-parse, no write.
4. Changed → new `source` row, new `result.revision`, and a `correction` entry. Never an in-place update.

Registry writes are already keyed deterministically (`contest` on `(election, place_version)`, `candidacy`
on `(contest, person)`), so a second run over identical bytes is a no-op.

## 24. Resumability strategy

`manifest.tsv` is the checkpoint. Each of DISCOVER → DOWNLOAD → HASH → PARSE → NORMALIZE → VALIDATE →
IMPORT → REPORT records per-artefact status, so a re-run resumes at the first artefact not marked `OK`.
Downloads themselves resume mid-file via `Accept-Ranges: bytes`. Import runs inside a `SAVEPOINT` per
artefact, so a mid-file failure rolls back that artefact alone and the rest of the run stands.

## 25. Validation strategy

Checks the sources make possible, with the numbers to assert:

1. **Seats per election** — 2024 LS = 542 in report 33 **+ Surat = 543**; WB 2026 = 294; Bihar 2025 = 243.
2. **Winners = seats.** Report 2 row count must equal the seat count (WB 2026: 294 winners, 309 sheet rows
   including headers).
3. **Report 33 ↔ report 13 join is total** — 542/542, zero collisions. A regression if it ever isn't.
4. **Vote arithmetic per row:** `GENERAL + POSTAL = TOTAL`. Bankipur: 64117 + 34 = 64151. ✓
5. **Constituency totals:** Σ candidate totals = the report's `TOTAL` row. Bankipur: 129588 EVM + 79 postal
   = 129667. ✓
6. **Cross-source agreement.** Bankipur on the live portal (64117/34/64151, EVM total 130233) matches the
   Index Card exactly. Where portal and report disagree, the report wins and the disagreement is recorded.
7. **`no_of_ac` vs seats found.** This already fails once: the schedule API reports **Telangana 2023
   `no_of_ac = 199`**; Telangana has **119**. Every other state agrees exactly (Rajasthan 200, MP 230,
   WB 294, Bihar 243, …). A transposition typo in ECI's own data — record it, do not silently trust either
   number.
8. **Phase seat counts sum to the total.** WB 2026: 152 + 142 = 294. ✓
9. **NOTA exactly once per constituency** — 542 NOTA rows for 542 PCs in report 33. ✓
10. **Every candidate has an age** — 8,359 of 8,359 for GE 2024. A drop below 100% is a parser bug.

## Recommended ingestion order

Value per unit of risk, highest first. Each step is independently shippable.

1. **Schedule API — 20 requests.** Replaces the derived five-year-term dates on the home page with
   announced ones. No parser, no schema change, immediate and visible.
2. **2024 Lok Sabha — reports 33, 13, 2, 7, 1, 16.** Six files. Takes Lok Sabha 2024 from 42 seats to 543,
   with 8,359 sourced candidate ages.
3. **2026 assemblies — 5 × report 10 + report 2.** West Bengal 2026 currently holds declared winners with
   `votes = 0`; this replaces them with real counts.
4. **2024–2025 assemblies — 10 elections** (8 × 2024, Delhi 2025, Bihar 2025).
5. **2023 assemblies — the 4 that exist** (Mizoram, MP, Rajasthan, Telangana).
6. **By-elections — 121 constituency files** across 8 windows, 2023–2026.
7. *(deferred)* Live portal, for counting-day only.
8. *(deferred)* Index Cards and per-AC PDFs, once PDF extraction is worth building.

# A. READY FOR DETERMINISTIC ECI INGESTION

Discovery is a three-request deterministic walk with no search engine in it. Every artefact in the
recommended path downloads over HTTPS to a byte-stable document with a `Last-Modified`, hashes
reproducibly, and parses with Node built-ins alone — proved on 8,901 rows of BIFF8 and 3,516 of
SpreadsheetML, not asserted. Provenance fits the existing `source` table with no schema change; no
headless browser, no PDF parser and no OCR is required; and `robots.txt` excludes nothing.

**What this decision does not cover**, stated plainly so it is not read as coverage it isn't:

1. **Five 2023 assembly elections cannot be ingested from ECI.** Chhattisgarh has no statistical report at
   all; Tripura, Meghalaya, Nagaland and Karnataka are listed on `old.eci.gov.in` with dead downloads.
   These must remain **absent**. The nearest authoritative alternative is the relevant **State CEO site**
   (SECONDARY), which this reconnaissance did not investigate and which should be a separate, scoped
   exercise. TCPD is easier and must not be used for them.
2. **Which constituency polled in which phase is not published machine-readably.** `Contest.phaseN` stays
   NULL; per-phase seat counts are the granular limit.
3. **Lok Sabha notification, nomination, scrutiny and withdrawal dates exist only in press-note PDFs.**
   Leave them absent rather than derive them.
4. **These reports are ECI's own secondary data.** Form 20 is the statutory record and remains
   un-ingested; the disclaimer travels with every row.

Nothing above blocks Phase 1. Items 1 and 3 are absences to be published as absences, which is what this
registry does with everything it cannot source.
