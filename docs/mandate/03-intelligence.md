## §12 Data model

### The conceptual model

Three rings. The inner ring is the asset; the middle ring is the volume; the outer ring is the
trust.

```
                    ┌─────────────────────────────────────────┐
                    │  RING 3 · PROVENANCE                    │
                    │  source · claim · citation · ingest_run  │
                    │  parser_version · correction            │
                    │  ┌───────────────────────────────────┐  │
                    │  │  RING 2 · FACTS  (columnar)       │  │
                    │  │  result · round_result            │  │
                    │  │  booth_result · turnout           │  │
                    │  │  ┌─────────────────────────────┐  │  │
                    │  │  │  RING 1 · REGISTRY  (OLTP)  │  │  │
                    │  │  │  person · party · place     │  │  │
                    │  │  │  election · contest         │  │  │
                    │  │  │  candidacy · alliance       │  │  │
                    │  │  │  ← THE MOAT                 │  │  │
                    │  │  └─────────────────────────────┘  │  │
                    │  └───────────────────────────────────┘  │
                    └─────────────────────────────────────────┘
```

### Ring 1 — the registry

**`person`** — the hardest table in the product. India has no national politician identifier.
The same human appears in ECI nomination data, MyNeta affidavits, PRS legislative records, court
dockets, and gazette notifications under different transliterations, with and without honorifics,
with inconsistent initials, and occasionally with a different stated age.

```
person(id, canonical_name, canonical_name_script, sex, birth_year?, birth_year_confidence,
       created_at, confidence, review_state)
person_alias(person_id, name, script, source_id, first_seen, kind)
      kind: eci_nomination | affidavit | prs | court | gazette | press | user_submitted
person_identifier(person_id, scheme, value, source_id)
      scheme: eci_candidate_id | myneta_id | prs_id | sansad_id | pan_masked | affidavit_no
person_merge(surviving_id, merged_id, decided_by, decided_at, evidence[], reversible)
person_split(original_id, into_ids[], decided_by, decided_at, evidence[])
```

**Resolution pipeline, four stages, with a human gate:**

1. **Blocking** — candidate pairs generated by phonetic key (a Devanagari/Bengali-aware variant
   of Double Metaphone; naive Soundex fails badly on Indic names), constituency overlap, and
   party overlap.
2. **Scoring** — a feature vector: name similarity across scripts, birth-year proximity,
   constituency history overlap, party history overlap, shared affidavit identifiers, co-occurrence
   in the same contest (a hard *negative* — two candidates in one contest are never the same
   person).
3. **Auto-merge** above a high threshold, **auto-reject** below a low one, **human queue** in
   between. The queue is a staffed, first-class internal tool, not a script.
4. **Audit** — every merge is reversible and logged with its evidence. A politician disputing
   their profile must be answerable with a record, not a shrug.

*Target:* < 1% incorrect merges on a 200-record random audit per release, published on
`/methodology/entity-resolution`. Publishing the error rate is the credibility move.

**`party`** — versioned, with lineage.

```
party(id, name, short_name, script_names{}, kind, ecI_status, registered_on, dissolved_on?)
      kind: national | state | registered_unrecognised | independent_bloc
party_version(id, party_id, valid_from, valid_to, name, symbol_id, hq_place_id)
party_lineage(from_party_id, to_party_id, kind, effective_on, source_id)
      kind: split | merge | rename | symbol_transfer | derecognition
symbol(id, name, name_script{}, svg_ref, allotment_kind, licensed_from)
```

Lineage is not a nicety. "The BJP in 1980" and "the Bharatiya Jana Sangh in 1971" are connected
but distinct; the Shiv Sena and NCP splits produced two claimants each to one symbol. A model
without lineage edges will silently produce wrong historical series, which is worse than
producing none.

**`place`** — hierarchical and **boundary-epoch versioned**.

```
place(id, kind, parent_id, canonical_name, names{script}, lgd_code?, eci_code?)
      kind: nation | state | ut | division | district | pc | ac | ward | booth
boundary_epoch(id, name, effective_from, effective_to, source_id)
      e.g. 'delimitation-1976', 'delimitation-2008', 'delimitation-2027?'
place_version(id, place_id, epoch_id, number, reservation, geometry_ref, electors_at_creation)
      reservation: general | sc | st
place_crosswalk(from_place_version_id, to_place_version_id, area_share, population_share,
                elector_share, method, source_id)
```

`place_crosswalk` is the single most valuable table nobody builds. It is what allows an honest
answer to "how did this seat vote in 1999?" when the seat did not exist in 1999. The answer is
an *estimate with a stated method and stated weights* — and the UI must label it as an estimate
every single time it appears. The next delimitation, constitutionally deferred to the first
census after 2026, will make this table the difference between a platform and a museum.

**`election`, `contest`, `candidacy`** — the contest is the atomic unit.

```
election(id, kind, level, jurisdiction_place_id, epoch_id, name,
         electorate_kind, lifecycle_state, announced_on, notified_on, counting_on)
      kind: general | assembly | biennial_rs | municipal | panchayat | bypoll | presidential
      level: union | state | district | block | ward
      electorate_kind: direct | indirect | electoral_college
election_phase(election_id, n, poll_date, seat_count, states[])
contest(id, election_id, place_version_id, phase_n, seats_available,
        lifecycle_state, declared_at?)
candidacy(id, contest_id, person_id, party_version_id?, alliance_id?, symbol_id,
          serial_no, status, age_declared, education_declared)
      status: filed | rejected | withdrawn | contesting | elected | defeated | disqualified
```

`electorate_kind` is how Rajya Sabha (indirect, MLAs voting, single transferable vote) and
panchayat elections live in the same schema as Lok Sabha without a parallel universe of tables.
It changes the *result interpretation*, not the shape.

**`alliance`** — versioned membership, because NDA-2019 ≠ NDA-2024.

```
alliance(id, name, names{script})
alliance_version(id, alliance_id, valid_from, valid_to)
alliance_member(alliance_version_id, party_id, joined_on, left_on, seat_share_agreed?)
```

### Ring 2 — the facts

Columnar, append-mostly, immutable-with-supersession. Never updated in place: a revised figure
is a new row with a higher `revision` and the old row stays readable, because the correction
ledger (§6.10) depends on it.

```
result(contest_id, candidacy_id, revision, votes, postal_votes, evm_votes,
       vote_share, rank, is_winner, margin, source_id, ingested_at)
round_result(contest_id, round_no, candidacy_id, votes_cumulative, source_id, observed_at)
booth_result(contest_id, booth_place_id, candidacy_id, votes, source_id)   -- Form 20
turnout(contest_id, scope, electors, voters, male, female, third_gender, postal, nota, source_id)
```

**Scale, honestly.** ~1.05 M polling stations × ~10 candidates × 3 recent general elections is
already tens of millions of rows before assemblies, and Form 20 is published as PDFs of varying
quality, state by state, with no consistent schema. This is the largest single cost in the plan
and §28 phases it in one state at a time rather than pretending it is a sprint.

### Ring 3 — provenance

```
source(id, kind, publisher, title, url, archived_url, retrieved_at, published_on,
        doc_hash, page_count, licence)
      kind: eci_form20 | eci_declaration | eci_notification | affidavit | gazette |
            court_order | prs_record | party_return | census | secc | press | factcheck
source_page(source_id, page_no, ocr_text, ocr_confidence)
claim(id, subject_entity_ref, predicate, object_value, unit, as_of, confidence)
citation(claim_id, source_id, page_no?, rect?, extracted_by_parser_version, extracted_at)
ingest_run(id, pipeline, parser_version, started_at, finished_at, rows_in, rows_out,
           anomalies[], status)
correction(id, entity_ref, field, old_value, new_value, reason, source_id, corrected_at,
           public_url)
```

**The provenance invariant:** every value rendered in the product resolves to ≥1 `citation`
with a `source_id`. Enforced at three levels — a not-null constraint in the fact tables, a
required `citations` prop in `@mandate/viz`, and a contract test per API endpoint asserting
`sources.length > 0`. Three levels because this is the one property the product cannot ship
without.

### Derived layer

Materialised, versioned, and each with a model card at `/methodology/:measure`:

`seat_flip` · `swing_pp` · `enp` (effective number of parties, Laakso–Taagepera) ·
`index_of_opposition_unity` · `competitiveness_class` · `incumbency_retention_rate` ·
`turnout_deviation_from_district` · `vote_to_seat_elasticity` · `party_momentum` ·
`asset_growth_cagr` · `contest_footprint`

Derived values carry `derived_from[]` so their provenance chains back to primary sources. A
derived number's citation set is the union of its inputs' citation sets, computed, not curated.

### Data governance

- **No PII beyond the public record.** Affidavits are public documents; we publish what they
  publish and no more. Addresses are shown at constituency granularity only. PAN and similar
  identifiers are stored masked and never rendered.
- **Right of reply.** Every person page carries a documented dispute path, and a disputed field
  renders with a `ConfidenceChip` of `disputed` until adjudicated.
- **Licence tracking per source.** Census, SECC, PRS, and party symbol assets all have distinct
  terms. `source.licence` is not decorative — the bulk-download surface (§7) filters on it.

## §13 Analytics layer

### The semantic layer

Analysts do not write SQL against our physical schema, and the AI layer must not either. Both
go through a declared semantic layer: **dimensions, measures, and joins, named once.**

```yaml
measure margin_pct:
  label: "Margin"
  unit: percentage_points
  sql: (winner_votes - runner_up_votes) * 100.0 / valid_votes
  grain: contest
  requires: [result]
  model_card: /methodology/margin_pct
  caveats:
    - "Undefined for uncontested seats and for multi-member contests."

dimension boundary_epoch:
  label: "Boundary epoch"
  values: from boundary_epoch
  warn_when_crossed: >
    Comparing contests across boundary epochs uses crosswalk estimates.
    Every affected figure is labelled as an estimate.
```

Three properties earn the layer its keep:

1. **One definition of turnout.** The most common failure of election dashboards is three
   different turnout numbers on three pages, because three people wrote three queries. Here,
   `turnout_pct` exists once.
2. **Caveats travel with the measure.** A measure used in a context where its caveat applies
   renders the caveat on the card. The epoch-crossing warning fires automatically.
3. **The AI layer can only emit valid queries.** Its output space is *this vocabulary*, not
   arbitrary SQL (§14). This is the single most important safety property in the AI design.

### The cross-filter engine

The interaction target is *instant* filtering — the Bloomberg feel — which server round-trips
cannot deliver at Indian network latency.

**Approach:** the server ships a **Parquet slice** for the current analytical scope (one
election × one state, typically 2–20 MB compressed), the browser loads it into **DuckDB-WASM**,
and every subsequent filter, group-by, and re-aggregation runs locally in single-digit
milliseconds. Slices are content-addressed and cached in the Cache API, so the second visit to a
state is instant and the third is offline-capable.

```
first load   ─→ server: /v1/slice/ls-2024/wb.parquet   (≈6 MB, HTTP-cached, immutable)
               ─→ DuckDB-WASM registers it
filter/drill ─→ local SQL, 2–15 ms, no network
escalate     ─→ /v1/query for cross-state or booth-level (ClickHouse, 100–400 ms)
```

Escalation is explicit and visible: a card that needs the server shows a brief inline
"computing across 4,120 seats" state rather than pretending everything is local.

*Skipped for MVP:* booth-level slices in the browser. A single state's booth data exceeds a
reasonable download. Booth analysis stays server-side until measured demand justifies a
tiled-slice design.

### Chart form selection

The form is chosen by the data's job, and the choice is a documented function, not a
preference. Applied to this domain:

| Job | Form | Domain example |
|---|---|---|
| One headline | Stat tile / hero number | "Turnout 65.8%" |
| Magnitude, few categories | Horizontal bar, sorted | Vote share in one contest |
| Magnitude, many categories | Sorted bar + virtualised table | All 4,120 seats by margin |
| Composition of a whole | Single stacked bar (`SeatBar`) | Seat composition by alliance |
| Change over time | Line | Party vote share 1952→2024 |
| Change, two points | Slope / dumbbell | 2019 vs 2024 by state |
| Distribution | Histogram / strip | Margin distribution |
| Two measures | Scatter | Turnout vs margin, 543 points |
| Spatial magnitude | Choropleth (sequential) | Turnout by district |
| Spatial polarity | Choropleth (diverging) | Swing to/from incumbent |
| Spatial identity | Choropleth (categorical, ≤3 hues + texture) | Winning party — see §24 |
| Flow between states | Sankey | Estimated vote transfer between cycles |
| Hierarchy of magnitude | Treemap | Seats by state within alliance |
| Relationship | Network | Influence network |
| Uncertainty | Range plot | Forecast intervals |
| Many small comparisons | Small multiples | Per-state trend, 31 panels |

**Two hard prohibitions.** No dual-axis charts, ever — two measures at different scales become
two charts, small multiples, or an indexed series. And no pie chart with more than two slices;
seat composition is a `SeatBar`, which is readable at 4,120 seats and a pie is not readable at
five.

### Analytics Studio

A canvas, not a wizard. Drop a dimension and a measure; the form heuristic proposes a chart; the
user can override. Every studio analysis is a `Card[]` (§9), so it saves as a board, exports as
CSV/PNG/SVG, embeds as an iframe with the citation footer baked in, and can be handed to the AI
layer to explain.

Template analyses ship as first-class content, because a blank canvas is a wall:
*Seats at risk* · *Swing map* · *Turnout anomalies* · *Money in politics* · *Women's
representation* · *Criminal cases by party* (titled "Candidates with pending cases, by party" —
P5) · *Youngest and oldest legislatures* · *Vote-share to seat-share conversion*.

### Reproducibility

Every chart exports with a **provenance footer**: measure definitions used, filters applied,
data version, slice hash, and the citation set. Rohit's persona (§3) is unserveable without
this, and it is also the thing that makes our charts safe to screenshot into a newspaper.

## §14 AI layer

### The one architectural decision

**The AI does not write prose over documents. It compiles questions into semantic-layer
queries, and returns a card.**

```
question ─→ [intent classify] ─→ [entity resolve] ─→ [query compile] ─→ [validate] ─→ execute
                                                                              │
                                                       ┌──────────────────────┴───────┐
                                                       │ Answer                        │
                                                       │  · one-sentence finding       │
                                                       │  · the Card (chart or table)  │
                                                       │  · the query, shown, editable │
                                                       │  · citations[]                │
                                                       │  · caveats[] from the measures │
                                                       └───────────────────────────────┘
```

Why this and not retrieval-augmented generation over the corpus: RAG over political documents
produces fluent, plausible, uncheckable sentences, which is precisely the failure mode this
product exists to eliminate. A compiled query is verifiable — the user can read it, edit it, and
re-run it. When the model is wrong, the wrongness is visible in the query rather than hidden in
the prose.

**Consequence:** the model's output space is constrained to a validated grammar. If the compiler
cannot produce a valid query, the system **abstains** with a specific reason ("no measure exists
for candidate net worth at the booth level") and offers the nearest answerable question.

### Capabilities, in build order

1. **Entity jump** — "diamond harbour 2024" → the contest. Not really AI; it is search, and it
   is 60% of the value.
2. **Query compilation** — "which seats flipped in Bihar in 2025", "compare BJP and Congress
   vote share in Bihar since 2005", "seats where the winner's margin was under 2%".
3. **Entity summarisation** — a person, party, or contest summarised *from the structured record
   only*. Every sentence is generated from a template bound to a specific field with a citation.
   Reads slightly stiff. Never wrong.
4. **Explanation** — "why is this constituency competitive?" answers by naming the measures that
   put it in the competitive class and showing them. It explains the *classification*, not the
   politics.
5. **Briefing generation** — a scheduled artefact (daily, or per counting round) assembled from
   cards, with every figure cited. Deliverable as email, PDF, or a board.
6. **Anomaly narration** — turns a fired rule into a readable lead: "This candidate's declared
   assets grew 640% between filings. Both affidavits are attached."

### Hard guardrails

- **No claim without a citation.** A generated sentence whose figures cannot be traced to
  citations is dropped before render, not flagged.
- **No forecast during a gated period.** The compliance gate (§6.10) is applied in the API,
  so the AI physically cannot return a suppressed measure.
- **No inference about protected attributes of individuals.** The model never infers a person's
  religion or caste. Aggregate demographic data about *places* comes from Census/SECC with a
  vintage label; it is never attached to a named individual.
- **No causal language.** "Correlates with", never "because of". Enforced by a post-generation
  lexical filter, which is crude and effective.
- **No answer about a person's guilt.** Case stages are reported (P5); the model does not
  characterise them.
- **Abstention is a success state.** Tracked and published: abstention rate, citation coverage,
  and query-validity rate go on `/methodology/ai`. A model that never abstains on a corpus this
  incomplete is lying.

### Evaluation

A golden set of ~500 questions across the personas, each with a known-correct query and answer,
run on every model or prompt change. Four metrics: **query validity** (compiles and executes),
**answer correctness** (matches the golden result), **citation coverage** (fraction of figures
traceable), **appropriate abstention** (abstained when it should, answered when it should).
Regressions block deploy. The golden set is versioned in the repo and grows from real
abstentions and real complaints.

## §15 Map experience

### Not an SVG

The current product renders West Bengal as an inline SVG path set
([src/data/wb-ac-paths.ts](../../src/data/wb-ac-paths.ts), 168 KB). That does not scale to
543 parliamentary constituencies, ~4,120 assembly constituencies, ~780 districts, and ~1.05 M
booths — nor to boundary epochs, where the same place has multiple geometries.

**Architecture: MapLibre GL JS + PMTiles.** Vector tiles are built offline with `tippecanoe`
from delimitation shapefiles and served as a **single PMTiles archive on object storage with
HTTP range requests** — no tile server, no per-tile function invocations, cheap at any traffic
level, and trivially cacheable at the edge.

```
shapefiles (ECI / LGD / delimitation orders)
   → clean + validate topology + attach place_version_id
   → tippecanoe → PMTiles archive per boundary epoch
   → object storage + CDN
   → MapLibre reads via range requests; data joined client-side by place_version_id
```

**Tilesets:** `states` (z0–4) · `districts` (z3–8) · `pc` (z3–10) · `ac` (z4–12) ·
`wards` (z9–14) · `booths` (z11–16, points, clustered). One archive per `boundary_epoch`, so
switching epochs switches basemap geometry — which is the only correct way to render a
delimitation change.

**Critical separation:** geometry lives in tiles; *values* arrive from the API and are joined at
runtime by `place_version_id` using MapLibre's `setFeatureState`. This means a new measure is a
JSON fetch, not a tile rebuild, and the same tiles serve every layer in the registry.

### The layer registry

Layers are data, not code. Adding one is a registry entry.

```ts
type Layer = {
  id: string
  group: 'electoral' | 'demography' | 'development' | 'administrative'
  label: string
  encoding: 'sequential' | 'diverging' | 'categorical' | 'point' | 'boundary'
  measure: MeasureRef            // resolved through the semantic layer
  domain: 'auto' | [number, number]
  vintage: string                // shown on the legend, always
  sources: SourceRef[]
  availableAt: PlaceKind[]
  minZoom: number
}
```

**Shipped groups.** *Electoral:* winner by party, vote share, margin, margin band, turnout,
swing, seat flip, NOTA share, postal share, historical winner by year, competitiveness class,
uncontested. *Demography:* electors, elector growth, sex ratio of electors, literacy,
urbanisation, workforce composition, SC/ST proportion, religious composition — **all Census/SECC,
all vintage-labelled on the legend, none of it joined to individuals.** *Development:*
MPLADS/MLALADS utilisation, road and electrification indices, district development indicators.
*Administrative:* boundary epoch, reservation status, delimitation diff, polling-station density,
electors per station.

Layers we do **not** ship: caste composition below the aggregate published level (the data does
not exist at constituency granularity and estimating it invites misuse), and any crime layer
keyed to a place, because place-level crime statistics attached to an electoral map is an
invitation to a conclusion the data cannot support. Both refusals are documented in the
methodology rather than silently omitted.

### Interaction

- **Hover is the product.** Immediate feature card: constituency name in both scripts, winner
  with party symbol, vote share, margin, turnout, and a 4-election sparkline. No click required.
- **Click** pins the feature to an inspector panel; a second click opens the place entity in a
  new tab.
- **Search inside the map** — `⌘K` filters to places when the map has focus, and selecting one
  flies to it.
- **Compare mode** — swipe divider, side-by-side, or **difference** (computed delta rendered as
  a diverging choropleth). Difference across boundary epochs uses the crosswalk and says so on
  the legend.
- **Booth mode** at z ≥ 11 — polling stations as points sized by electors and coloured by winner,
  which is the most striking view in the product and the one nobody else has.
- **Keyboard** — arrow-key pan, `+`/`-` zoom, `Tab` through visible features with the inspector
  following focus. A map that is mouse-only is inaccessible; feature-by-feature keyboard
  traversal plus the table view (below) is the accessible path.
- **Every map has a table view** (`t`). The choropleth is the fast read; the table is the
  accessible and citable one.

### Colour on maps (the computed constraint)

A choropleth is an **all-pairs** colour problem: any two regions can be adjacent, so every pair
of series colours must be distinguishable, not just the ones next to each other in a legend.
Running the validator on the dark surface:

```
3 hues, all pairs:  PASS  (worst CVD ΔE 9.4 deutan, worst normal-vision ΔE 20.9)
4 hues, all pairs:  FAIL  (violet↔blue ΔE 1.9 protan, 9.8 normal-vision)
```

Therefore **a party-winner map renders at most 3 hues.** Beyond three parties: the leaders folded
into "Other" carry a **texture fill** (45°/135° hatch) plus the party symbol on the label, and
the legend is always present. The alternative default — "give every party its brand colour" —
produces a map that a large fraction of readers cannot decode, as the §2 P3 validator run shows.
Sequential and diverging layers are unaffected: one hue light→dark for magnitude, two hues with a
grey midpoint for polarity, never a rainbow.

### Performance

Boundary simplification per zoom at tile build; `setFeatureState` for value updates rather than
re-tiling; a single archive per epoch fetched by range so first paint needs ~200 KB; hover
handled on the GPU via feature state, not React re-render. Target: first meaningful map in
< 1.5 s on a 4G connection, and 60 fps pan at national zoom.

## §16 Live election experience

### The unit of time is the round, not the second

Indian counting proceeds in **rounds** — typically 14 EVMs per table per round, 15–25 rounds per
assembly segment. Round boundaries are when numbers actually change; a per-second ticker over
round-granular data is theatre. The live product's clock is `round n of m`, per contest, and the
national view aggregates rounds.

### Mode transition

Live is a **mode**, not a page (the user's requirement, and the right call). When an election
enters `counting`:

- The **Ink Strip** becomes the national tally: a live `SeatBar` by alliance, the declared count,
  and a lead-change ticker.
- The **rail** grows a ninth, temporary item: **Counting**, auto-selected on first visit.
- Every **contest Brief** replaces its result card with the live round card.
- The **map** switches to `live_leader` with a "declared vs leading" texture distinction.
- **Forecast surfaces stay suppressed** until the compliance gate releases (§6.10).
- On exit, everything reverts and the mode's artefacts (the round timeline, the lead-change log)
  become permanent parts of the contest's Investigation floor. **Counting day generates archival
  value, not disposable UI.**

### The calling discipline

The credibility of the entire platform is decided in about six hours, once every few years.

1. **We never call a seat.** `LEADING` and `WON` are different states with different typography
   (regular vs semibold), a different mark, and different words. `WON` appears **only** after the
   returning officer's declaration is ingested from an ECI source.
2. **Every live figure is `provisional`** until the final declaration, and carries the chip.
3. **Round provenance.** Each round figure records where it came from and when it was observed.
4. **Revisions are visible.** Counting figures get revised. A revised value flashes once, states
   the change, and keeps the prior value in the round timeline. Silently overwriting a number on
   counting day is unforgivable and permanently discrediting.
5. **Disconnection is stated, not hidden.** "Feed disconnected 40 s ago. Retrying. Figures shown
   are from 17:42 IST." A live product that silently shows stale numbers is worse than one that
   is visibly down.
6. **No projections from partial counts** unless the compliance gate is open, the model is
   published, and its historical accuracy is on the card. Otherwise nothing.

### Transport

```
ECI results endpoints  ─poll 20s─→  ingest workers (idempotent, hash-deduped)
                                        │  parse → validate (Zod) → diff vs last state
                                        ▼
                                  ClickHouse (round_result, append-only)
                                        │
                                  Redis Stream per election  (the fan-out spine)
                                        │
   ┌────────────────────────────────────┼────────────────────────────────────┐
   ▼                                    ▼                                    ▼
SSE /v1/live/:election/stream    snapshot /v1/live/:election      pre-rendered ISR pages
(deltas only, ~1–3 KB/event)     (full state, for cold start)     (crawlers, share cards)
```

**Server-Sent Events, not WebSockets.** The data flow is one-directional, SSE survives proxies
and mobile networks better, reconnects with `Last-Event-ID` for free, and needs no separate
server. WebSockets would buy bidirectionality we do not use.

**Cold start then deltas:** a client fetches the snapshot, then subscribes from that sequence
number. `Last-Event-ID` on reconnect replays the gap, so a tunnel or a lift does not desync the
page.

**Load shape.** Counting day is a 100–1000× traffic spike for six hours, once a cycle. Design
for it: the snapshot is a CDN-cached object with a 10-second TTL (so a million cold starts cost
one origin read per ten seconds), SSE fan-out scales horizontally off the Redis stream, and there
is a **static degraded mode** — a pre-rendered tally page regenerated every 30 seconds — that
serves if the live tier fails. A degraded page that is 30 seconds old beats an error page by an
infinite margin.

### "While you were away"

Return after 60 seconds and a dismissible bar states the diff: *"12 seats declared, 3 lead
changes, NDA +7 since 17:42."* Then `⌥⇧R` replays the interval on the map at 8× speed. This is
the single most delightful thing in the product and it costs almost nothing, because the round
timeline is already stored.
